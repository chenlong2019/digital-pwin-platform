## 0. 一句话结论

**两份文档不是一回事。** 架构文档管「包怎么切」，本产品规格管「业务闭环跑没跑通」。
两者不冲突，但**优先级相反**：架构文档要求先拆包，产品规格 §17 要求先把闭环跑通。

据此建议：**已拆的包不回退；但阶段 3 的拆包改名（`grid-inspection → power-mission`）暂停**，
改为补齐 P0 业务闭环缺口 —— 因为前者对用户不可见，后者才是 §15 验收用例要考的东西。

### 拆包这一处的裁定（唯一实质冲突）

规格说：*「只有当第二个业务场景或真实复用需求出现时，再把稳定能力提取为独立包。」*

- 本项目**第二个业务场景已经存在**：`vehicle-agent` + 汽车沙盒（`/car`），
  且它没有污染内核 —— §119-1「换 Agent 不改 Core」已实际通过。
- 阶段 1/2 的拆包是**零行为变更的纯搬迁**（类型靠编译器兜住，173 项单测全绿）。

所以拆包不是「为未来预支」，是**已经开始兑现**。**结论：已拆不回退。**

但**剩下的阶段 3 只做改名与目录细分、对用户零可见**，应当让位给 P0 闭环缺口。

## 3. §15 七个验收用例对账

| 用例 | 通过度 | 已满足 | 缺口（可定位） |
| --- | --- | --- | --- |
| **A 正常巡检** | ⚠️ 4/6 | 生成并预览巡检点及航线；无人机按线执行并落结果；结果页有完成率/照片数/耗时；Replay 显示轨迹与事件 | ❌ **不能「创建并保存任务」**（无 `MissionDefinition` 持久化）；❌ 结果页**无能耗**统计 |
| **B 检查点漏检** | ✅ 3/3 | 结果不会显示 100% 覆盖；能定位漏检点并给出原因（`DetectionResult.note`）；**可禁用 / 移除检查点**（`RouteShot.enabled`，禁用的点不飞但部位仍计入分母） | —（2026-10-09 补，见 §4.1） |
| **C 安全距离违规** | ❌ 0/4 | △ 有前视避障探测（`flight-control.ts`）与 `geofence` 盒 | ❌ 无「安全距离」规则；❌ 无 SafetyEvent（时间/位置/目标/测量值/阈值）；❌ 执行页与结果页无展示；△ 事件定位仅日志文本，非空间定位 |
| **D 低电量返航** | ✅ 2/3 | 电量模型 + 低电量/严重低电量自动返航（`drone-agent/drone-sim.ts`）；结果标注完成/中止 | △ 触发原因进了事件流，但**未进「结果页未完成项」的结构化字段** |
| **E 采集失败** | ✅ 3/3 | 采集失败记入记录、不判通过、原因可追溯；**检查点表里逐条给出六项检查与未通过原因**（2026-10-09 补） | — |
| **F 历史记录** | ❌ 0/2 | △ 回放能保存 | ❌ 回放是**单槽**（`replay-store.ts` 的 `simulation.replay.latest`），**无 MissionRun 列表**；❌ 无「改定义不影响旧记录」（因为既无定义也无版本） |
| **G 报告一致性** | ✅ 2/2 | 报告数值与结果页同源（同一份记录）；**报告标注数据来源**（`DataSource`：仿真 / 设备 / 人工，§10 硬要求） | —（2026-10-09 补，见 §4.1） |

> 标 ✅ 的三行于 2026-10-09 补齐；剩余「❌」集中在 A（任务定义持久化 + 能耗）、C（安全规则与事件）、F（MissionRun 版本化），正是 §4 里还没动的 #3 / #4 / #7。

**口径差异（必须单独说，否则会误判为「已达标」）**

规格 §5.2 的点位状态是 **作业口径**：`Pending → Approaching → Inspecting → Passed / Warning / Failed / Skipped`。
当前 `InspectionOutcome` 是 **对账口径**：`命中 / 误报 / 漏检 / 正确排除 / 未采集` —— 它依赖**地面真值**，
真实系统根本拿不到（`power-evaluation/point/inspection-point-result.ts` 顶部注释也是这么写的）。

两者不能混用。当前界面把「结论」与「对账」分块显示**是对的**；但**点位的作业状态需要独立建模**，
不能把对账结果直接当成 `Passed/Warning/Failed/Skipped`。

## 4.1 已完成（本轮，2026-10-09）

| # | 缺口 | 落点 | 证据 |
| --- | --- | --- | --- |
| 1 | 点位作业状态 + 逐条件失败原因 | `power-evaluation/point/point-status.ts`（`evaluatePoint` 六条检查、`derivePointResults`、`summarizePointStatuses`） | 单测 6 例 + 报告「检查点结果」表 + `e2e/grid.spec.ts` |
| 2 | 任务预检查（含字段定位与修正方式） | `grid-inspection/mission-validation.ts`（`validateMission` / `canRunMission`） | 单测 6 例 + 面板「③ 任务预检查」；`createInspectionTask()` 内硬拦截 |
| 6 | 检查点启用 / 禁用 | `RouteShot.enabled` + `PlanRouteOptions.disabledShotIds` + 面板拍点 checkbox | 单测 3 例 + e2e「被禁用的点不飞但如实显示跳过」 |
| 8（一半） | 报告**数据来源标注** | `power-evaluation/report/inspection-report.ts` 的 `DataSource`（§10 硬要求：仿真 / 设备 / 人工不能混） | 单测 + 报告头 `data-source` |

**顺带修掉的两个飞行缺陷**（都是「功能本来就在、但跑不出正确结果」）：

1. **接近段刹不住** —— `flight-control.ts` 的转场律只按距离给杆（`距离/6`），一路满舵飞到很近才收杆，
   载具带着十几米每秒冲过悬停位（实测偏 8.3 m，观测距离 23.1 m 超出要求 12.5~17.5，6 个拍点判失败）。
   改为按剩余距离可刹停的平方根曲线（`approachBrakeDistanceM = 20.6`，取自载具 normal 挡 12 m/s ÷ 3.5 m/s²）。
   代价：整场巡检 340 s → 370 s（+9%），飞行里程 724.1 m 与计划航线 721.6 m 基本吻合。
2. **避障坐标错位** —— `drone-agent.syncEnvironment()` 把**世界坐标**的障碍盒直接塞进 `DroneSim`，
   而 `DroneSim.position` 是**以起飞点为原点**的局部坐标。出生点不在原点时，机体拿局部坐标去撞世界盒：
   巡检场景里机体在世界 (33.7,14,69.7)、离所有杆塔 30 米开外，却被判「贴着障碍物」，以 0.14 m/s 爬行 50 s
   直到转场超时。已在同步时平移到机体坐标（只平移不旋转：`heading` 本就是世界航向）。
   沙盒场景出生在世界原点、平移量为零，所以这个错位此前一直没暴露。

## 5. 建议的下一个单步

**上一轮推荐（已完成）**：#1（点位作业状态）+ #2（任务预检查）—— 都是纯函数 + 面板，落地即能单测；
且是 #3 的前置。**已做（本轮）**：#1 / #2 / #6 / #8 的数据来源标注。见 §4.1。

**下一个单步建议做 #3（MissionDefinition 持久化 + MissionRun 版本化）**，理由：

1. 它是用例 A（不能保存任务）与 F（回放单槽）唯一还缺的那一格，`replay-store` 的 localStorage
   模式可以照搬，不引入新依赖；
2. #1 与 #2 已经落地，§5.3 的「只有通过校验的任务才能进 `Ready`」现在有东西可挂了；
3. 做它需要先定「版本」语义（改定义生成新版本、不覆盖历史），这个决定会同时影响 #4（安全事件）
   与 #7（Finding），先定下来后面少返工。

**不建议现在做**：

- 阶段 3 拆包改名 —— 对用户零可见，不推进任何验收用例；
- 四模式重构（#10）—— 界面大改，应等业务对象（MissionDefinition / SafetyEvent / Finding）定型后再动。
